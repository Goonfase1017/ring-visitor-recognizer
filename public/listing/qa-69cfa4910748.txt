Q7. Data elements collected from Ring users
TEXT: From Ring: Ring account ID and email, OAuth access and refresh tokens, shared camera names, online status, video encryption flag, privacy zones and US state, webhook events (doorbell press or motion, device id, time) and a JPEG snapshot for each event. Q8. How each data element is used
TEXT: Ring tokens, account ID and email: link the accounts and call the Ring Partner API. Camera details: list cameras, black out privacy zones, skip encrypted cameras, and turn recognition off for cameras in IL, TX or WA. Events and snapshots: show the arrival log. Face templates: compare faces in that customer snapshots only with that customer enrollments to show a name. Account email, password hash and activity log: sign-in, security and the customer own history. Nothing is used for ads, analytics or training.

Q9. Handling of video metadata
TEXT: We do not download video clips. For each webhook event we keep the camera name, event time, event type, processing status and, if recognition is on, matched names with scores and a count of unknown faces. Snapshots are re-encoded without EXIF metadata. All records are AES-256-GCM encrypted, visible only to the owning customer, and deleted after 30 days or sooner on request. Webhook request ids are kept 73 hours only to drop duplicates.

Q10. Data minimization practices
TEXT: We store snapshots, not video, and no audio. Enrollment photos are discarded after the face template is made. Faces of non-enrolled people are never stored; they are only counted as unknown. With recognition off (the default) no face processing happens. Automatic deletion jobs run in code: arrivals and snapshots after 30 days, unfinished Ring links after 15 minutes, templates one year after last sign-in, activity logs after 12 months. Retention is reviewed with each release.

Q29. AI models used
TEXT: Face detection: OpenCV Haar frontal-face cascade. Face templates: MobileFaceNet (TensorFlow Lite, run with LiteRT on CPU) producing a 128-number template from a 112x112 face crop. Matching: cosine similarity against the same customer enrolled templates, threshold 0.75. All run inside our server. No third-party AI service, no LLM or generative AI, and no external face database.

Q30. Monitoring and maintaining model performance
TEXT: The model is pinned and never retrained, so it does not drift. Edge cases are handled conservatively: faces under 60 px, side views or poor light are not detected or fall below the 0.75 threshold and show as Unknown, never as a guessed name. Every match shows the score and snapshot so the customer can check it. The same logic applies to all customers. Accuracy has not been benchmarked on a labelled dataset; misidentification reports come via support email.

Q31. Model versions, updates and rollback
TEXT: The model file is bundled in the code repository and Docker image and versioned in Git with the code, so it changes only with a reviewed release. Each release is a tagged Git commit deployed to Render, and a previous deploy can be redeployed to roll back. Templates from one model version are not compatible with another, so a model change would require customers to re-enroll people, with notice, before it is released.

Q32. Helping users understand AI decisions
TEXT: Each named arrival shows the snapshot, the matched name and a match score in percent, with the note Matches can be wrong; check the photo. Faces below the threshold are shown as Unknown. The Terms (Recognition limits) explain that lighting, angle, image quality, ageing or look-alikes can cause errors and that results are informational, not identity verification. The in-app disclosure explains how matching works before consent.

Q40. Encryption at rest and in transit
TEXT: In transit: HTTPS/TLS for all browser traffic with HSTS, TLS to Ring APIs and TLS to the database. At rest: every stored record and snapshot is encrypted in the application with AES-256-GCM (random 96-bit IV per record, 128-bit auth tag) before it reaches the database. The 256-bit key is held only in the Render encrypted environment settings, never in code, logs or the database. Passwords use scrypt. Key rotation is a manual re-encryption step.

Q41. Data storage locations and systems
TEXT: Application: one Node.js container on Render (United States) that keeps no customer data on disk; images are processed in memory. Database: Postgres hosted by Neon on AWS us-east-2 (Ohio, United States), holding only AES-256-GCM ciphertext plus random ids and timestamps. Source code (no customer data) is on GitHub. There are no other data stores, caches or copies.

Q42. Data flow between systems
TEXT: Ring sends a signed webhook to our Render server, which verifies it and downloads the snapshot through the Ring Partner API. The server masks privacy zones in memory and, only if the customer consented and enrolled people, computes and compares face templates in memory. Results are encrypted and written to the Neon database. The customer browser reads its own data over HTTPS after sign-in. Nothing is sent anywhere else.

Q43. Backup procedures
TEXT: We make no separate backups or copies of customer data. The database runs on the Neon free plan, whose built-in point-in-time restore keeps change history for up to 6 hours (capped at 1 GB); there are no scheduled snapshots on that plan. That history contains only our AES-256-GCM ciphertext, and deleted data ages out of it within 6 hours. Code is versioned in Git so the service can be redeployed.
