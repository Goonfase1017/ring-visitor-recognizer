Security

Effective: November 13, 2026

Architecture

One Node.js service on Render (US) receives Ring events, runs face matching server-side, and stores encrypted data in its data directory. HTTPS is enforced by Render. Ring webhooks are verified with HMAC-SHA256.

Access control and audit logging

Every API that reads or changes personal data requires the owner's bearer token (compared in constant time). Each administrative and API access is logged with time, method, path, result, actor, and source IP, including refused attempts, along with webhook receipts, registrations, opt-outs, deletions, exports, and retention runs. Logs are kept 12 months.

Encryption at rest

Visitor records, face templates, consent records, events, and photos are encrypted at the application level with AES-256-GCM (random IV per file, authenticated). The key lives only in the hosting environment, never in source code.

Vulnerability management

  • GitHub Dependabot alerts and weekly dependency update checks.
  • npm audit runs on every push; high or critical findings block release.
  • Fix targets: critical within 7 days, high within 30 days, others at the next release.
  • Internal security review of authentication, webhook verification, and data handling before each release.
  • Third-party penetration testing has not been done yet; it is planned before usage grows beyond early adopters.

Incident response

  1. Detect: alerts from Render, Dependabot, audit-log review, or a report to the email below.
  2. Contain within 24 hours: rotate the owner token, Ring credentials, and encryption key as needed; take the service offline if data is at risk.
  3. Assess what data and which users were affected.
  4. Notify affected users and Ring without undue delay, and within 72 hours of confirming a breach of personal data, plus regulators where the law requires.
  5. Fix the cause, restore service, and write a post-incident review.
